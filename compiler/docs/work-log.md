## WS3 - Governed registry release - 2026-08-05

**Delivered:** Tracer-informed WS3-WS9 Codex work specifications; a versioned v2 registry set that leaves the executable WS1/WS2 capability contract unchanged; a data dictionary with identifiers, value-set, type/unit/cardinality, requiredness, owner role, retention/consent/access references, interoperability mappings, provenance, and lifecycle; a capability-governance sidecar bound to exact executable capability and data-concept digests; detached clinical, data-governance, and technical attestation contracts; a separately content-addressed release contract; fail-closed activation requiring exact set/release/attestation digests, three distinct roles and people, approved decisions, current lifecycle, current timestamps, and a caller-supplied signature verifier; an unpopulated human approval template; sealed synthetic positive and negative fixtures; and stable `CHWN-REG-007` through `CHWN-REG-015` diagnostics.

**Deviations:** Production signature verification is represented by a required verifier boundary rather than an invented trust store, key, or signing service. All executable approval evidence uses visibly `synthetic-test-*` identities. Real owners, policy references, organizations, keys, signatures, jurisdiction, effective dates, and approval decisions remain unset. **Defects found:** The first governed shape included a data dictionary without binding capability parameters to its concepts, which would have made the dictionary ornamental. The first activation path trusted callers to have used strict parsers and could therefore accept directly constructed models without recomputing their digests. The first role check did not prohibit one person from filling multiple required roles or future-dated attestations. **Root cause:** Previously independent capability, concept, and approval objects shared human-readable names but no mandatory cross-artifact digest/type/unit invariant. Trust was placed at parser entry points instead of re-established at the irreversible activation boundary. Role labels were checked as a set without checking the identity and time semantics of each attestation.

**Generalized guardrail:** A governed capability must bind each declared concept use to an exact concept ID, version, digest, direction, and parameter; the compiler checks that parameter and concept types and units agree. Every executable capability in a v2 set requires governance. ## WS5 - Canonical IR bridge and deterministic resolution - 2026-08-05

**Delivered:** A bounded Product-to-canonical adapter and strict content-addressed adapter contract; accounting for all seven Product sections through canonical mappings or a stable loss report; an exact, registered CHT local-data binding; a separately reviewed semantic-needs artifact bound to the exact registry-blind WS4 candidate digest; deterministic resolution against one governed registry set, activation result, and target profile; a content-addressed resolution lock; implementation-independent capability invocation; explicit handling of every registered technical status; distinct technical and clinical output namespaces; reviewed synthetic task intent; a root `bridge-product` command; four strict JSON schemas; and a synthetic vertical slice that compiles through the WS2 CHT bundle, local harness, and differential oracle.

**Deviations:** Prompt B output does not flow directly into resolution. It cannot know registry family/operation vocabulary, deployment status names, target configuration, or Product variable IDs without violating the registry-blind control or inventing facts absent from the manual. A separate reviewed semantic binding supplies those exact normalized fields but cannot contain a capability or implementation ID. Adapter v1 supports only the variable-bearing synthetic tracer and empty clinical-logic sections; any nonempty rule/module/predicate/phrase section stops with a loss report. The committed activation result and task intent are visibly synthetic E2 fixtures, not human approval or a production trust token.

**Defects found:** The initial bridge draft trusted an arbitrary `source_candidate_digest` without receiving and rehashing the source candidate, so review provenance could not be proven. Directly constructed Pydantic models could also bypass adapter and resolution-lock digest checks at exported function boundaries. Cross-layer testing found that date variables and the local LMP binding had omitted `calendar_date` even though the governed capability required that exact unit. Product's candidate status vocabulary and parameter names are intentionally more general than the governed executable contract, so direct candidate-to-registry matching would either fail valid cases or encourage fuzzy translation.

**Root cause:** Registry-blind source extraction, deployment-specific semantic normalization, approval, and executable selection are different trust stages, but the original WS5 wording treated "candidate needs" as though one artifact could safely serve all of them. Separately, type/unit invariants and content verification had been enforced at individual parsers rather than re-established across every exported composition boundary.

**Generalized guardrail:** The compiler verifies the canonical digest of the exact WS4 candidate before conversion, reparses and rehashes reviewed needs, adapters, governed registries, and resolution locks at use boundaries, and never uses candidate prose as a selector. Resolution is equality-only over family, operation, ordered parameter names/types/units, complete status set, target profile, subject scope, and approved governance. Wording changes cannot affect selection; semantic changes fail closed; zero and multiple exact matches have distinct diagnostics. Unknown Product fields, coercible values, provenance loss, unsupported sections, unregistered local reads, mutated candidates, direct-model tampering, registry reordering, and contract mismatches are automated negative tests. Date-like registry and local-data parameters carry explicit semantic units.

## WS6 - Bounded CHT productionization and topology-safe queues - 2026-08-06

**Delivered:** A Python-owned bounded CHT production builder and root `build-cht-production` command; exact binding to a governed registry activation, resolution lock, target profile, local-data registry, task registry, and reviewed runtime-variable registry; registry-selected lowering through an implementation-binding tuple rather than tracer-specific capability or output names; emission of only invoked extensions; a content-aware Python `tasks.js` composer with collision detection, managed composition state, byte-idempotent recomposition, preservation of unrelated rules, and exact rollback bytes; strict content-addressed topology-snapshot and queued-operation contracts; deterministic assignment resolution and mandatory re-resolution at assignment, execution, sync, and handoff boundaries; fail-closed stale, future, missing, ambiguous, changed-assignment, resolution-lock-mismatch, and tamper handling; separate official-harness and exact-target evidence records for CHT 4.22.0 and 5.2.0; and a production dependency inspection covering the complete Python CHT slice.

**Deviations:** WS6 deliberately productionizes only the already exercised single-contact vertical slice. It does not add FHIR, messaging, group-scoped obligations, general Product clinical-logic conversion, handset testing, deployment, or approval. The TypeScript implementation remains a test-only differential oracle and is absent from the production dependency graph. The deterministic bundle records official-harness and exact-target runtime checks as `not_run`; the separately executed pinned browser harness supports E3 only for its reviewed special-function fixtures and does not upgrade the new composed WS6 bundle to E3 or E4.

**Defects found:** The first queued-operation implementation hashed the caller's UTC timestamp spelling before strict Pydantic parsing normalized `+00:00` to `Z`, so a newly created operation failed its own digest verification. The first production dependency check inspected only three new modules, which could have missed a Node or subprocess dependency introduced through a sibling CHT lowering module. A red-team pass found that two invocations of the same capability would both pass validation although the lowerer selected only the first, that duplicate resolution-lock entries could collapse into a dictionary after the outer digest was recomputed, and that both WS2 and WS6 tested status-variable use with string containment, allowing `st_status_shadow` to masquerade as `st_status`. Architectural dependency evidence was scoped to files added in WS6 rather than the full runtime slice used by the entry point. The bounded lowerer and lock validator converted multiplicity into keyed lookup without first asserting uniqueness, which made duplicate inputs look like valid singletons. Status coverage inspected serialized text instead of expression structure, confusing identifier substrings with exact references. Test evidence can likewise be misclassified when a suite's pinned runner and environment are not treated as part of the evidence contract.

**Generalized guardrail:** Content-addressed topology and queue objects are first validated and normalized by their strict runtime model, then sealed over that canonical representation, and reparsed and rehashed at every exported use boundary. Re-resolution verifies the exact snapshot digest, resolution-lock digest, subject, operation ID, maximum age, and assignment cardinality; untrusted or stale state cannot silently retain an old assignee. The bounded production path rejects repeated capability invocations until multi-invocation lowering is explicitly designed, and it validates exact lock schema/rule/rationale/entry fields plus unique need and capability IDs before constructing any lookup. Status coverage now walks expression objects and accepts only an exact `{kind: var, id: ...}` reference in both the production and tracer siblings. The dependency inspection parses imports across production builder, backend, evidence, local-data, special-function, task-composition, task-binding, and topology modules and fails if Node, TypeScript-oracle, or subprocess dependencies appear. Automated tests cover alternate UTC spelling, reordered assignments, duplicate boundary events, re-signed duplicate lock entries, repeated capability invocations, identifier-substring attacks, every blocking state, exact task rollback/recomposition, and the complete inspected-module set. Only the pinned Product pytest command is counted as Product evidence; failed ad hoc invocations are explicitly not passes.
